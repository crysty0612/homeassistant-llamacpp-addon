# AI Memory: Home Assistant llama.cpp Add-on

## Project Overview
This repository contains a Home Assistant (HA) Add-on that runs `llama.cpp`. It provides a highly configurable interface directly inside Home Assistant, allowing users to pull models from Hugging Face, enable GPU hardware acceleration (Vulkan), and configure advanced text generation settings like Speculative Decoding (MTP/DFlash).

## Directory Structure
- `llamacpp/`: The core add-on directory.
  - `config.yaml`: Defines the Add-on settings, exposed ports (`8080/tcp`), device access (`/dev/dri`), and the schema for the configuration UI.
  - `translations/en.yaml`: Contains the human-readable names, descriptions, and validations for the fields in the UI.
  - `build.yaml`: Tells the HA Supervisor which architectures to build for (using `ubuntu:24.04` base).
  - `Dockerfile`: The build script. It is designed to be minimal. It does **not** compile `llama.cpp` from source. Instead, it queries `api.github.com/repos/ggml-org/llama.cpp/releases/latest` to download the officially compiled Ubuntu tarballs for both CPU and Vulkan for the correct architecture (amd64 or arm64).
  - `pull_models.py`: A Python script that uses `huggingface_hub` to download models, automatically identify `mmproj` (vision) files, and process optional Drafter models before the server boots.
  - `run.sh`: The bash entrypoint. It reads the execution config generated by Python, verifies GPU device paths if Vulkan is enabled, sets up `LD_LIBRARY_PATH` for the downloaded `.so` files, and constructs the final `llama-server` command.

## Configuration & UI Design
Because HA Add-on configuration schemas (`config.yaml`) are static, we cannot dynamically update a UI dropdown with a list of already downloaded models. 
Instead, the design relies on text inputs with strict RegEx validations (`match(^[^/]+/[^/]+:.+\.gguf$)`).
- **Main Model**: Required. Format `org/repo:filename.gguf`
- **Drafter Model**: Optional. Format `org/repo:filename.gguf`
- **Drafter Type**: Dropdown list (`none`, `mtp`, `dflash`)

## Model Execution & `llama.cpp` Limitations
`llama-server` is designed to run **one main model** at a time. The add-on is configured to boot that single model on port `8080`.
- **Multiple Instances**: If a user wants to run multiple models simultaneously, they must duplicate the add-on in Home Assistant and change the mapped host port in the Home Assistant "Network" configuration tab.

## Hardware Acceleration (Vulkan)
Vulkan support relies on passing the correct GPU block devices (e.g., `/dev/dri/renderD128`) to the Docker container. 
If `LLAMACPP_VULKAN` is checked in the UI, `run.sh` will explicitly check if `LLAMACPP_GPU_PATH` exists on the host. If the device path is missing, it crashes the boot process gracefully with an error, enforcing strict GPU validation.

## Testing the Add-on
A testing harness has been configured in the `test/` directory. Since Home Assistant Add-ons are just Docker containers that receive their configuration via a `/data/options.json` file, we can easily mock this locally.
- A mock `options.json` file resides in `/test/options.json`.
- Run `/test/test.sh` to automatically build the Docker image and start the container with the mock options.
- The repository includes an AI skill for this. You can refer to `.agents/skills/test-addon/SKILL.md` for complete testing instructions.

## Development Notes & Best Practices
- **Never compile from scratch**: The `Dockerfile` relies on official `ggml-org/llama.cpp` releases to keep image build times fast and sizes small.
- **Handling library paths**: Because the release tarballs contain dynamic libraries (`.so` files), `run.sh` explicitly exports `LD_LIBRARY_PATH` so `llama-server` can find its dependencies.
- **Troubleshooting**: `pull_models.py` outputs all downloaded models to the console at startup so users can see exactly what is cached in their `LLAMACPP_MODEL_DIR` by checking the Add-on Logs.
